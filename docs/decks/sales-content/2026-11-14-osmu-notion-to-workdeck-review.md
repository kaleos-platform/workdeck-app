# OSMU — 노션 기능을 Workdeck 로 합치는 방법 검토 (2026-11-14)

- 요청: 「노션 대신 발행 요청(1~3단계)을 할 경로」 — A(에밀리 도구)는 바로 진행, 노션 기능의 Workdeck 통합은 검토
- A 결과: `sc_request_post` main+prod(#1392→#1395). 에밀리가 노션 행을 만들고 즉시 처리한다(노션은 그대로 기록 창구)
- 관련: [설계](./2026-11-08-osmu-source-pipeline.md) · [인계](./2026-11-08-osmu-handoff.md)

## 1. 지금 노션이 맡는 일

| #   | 역할               | 노션에서의 모습                                                               | Workdeck 대체물                                                  |
| --- | ------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | **소재 입력**      | 「콘텐츠 소재」 행 — 항목(행사일·장소·기관·상품·미디어 폴더) + 자유 서식 본문 | 없음 (TipTap 에디터는 결과물용으로만 존재)                       |
| 2   | **발행 요청 입력** | 「콘텐츠 발행」 행 — 소재·유형·관점·희망일, 상태 「작성 요청」                | 에밀리 `sc_request_post`(A, 노션 행을 대신 만듦). 화면 없음      |
| 3   | **진행 상태 보기** | 「상태」 select(9개) — Workdeck 이 10분마다 되씀                              | 승인 화면·배포 내역은 있으나 「요청 단위」로 모아 보는 화면 없음 |
| 4   | 팀 공유·모바일     | 노션 앱                                                                       | Workdeck 은 웹(반응형)만                                         |

노션이 **원본(SSOT)인 것은 1(소재 원문)뿐**이다. 2·3 은 이미 Workdeck DB(`ScPublishRequest`)가 원본이고 노션은 복사본이다.

## 2. 노션을 유지할 때 드는 비용 (실제로 겪은 것 포함)

1. **이중 관리·지연**: 상태가 Workdeck → 노션 projection(cron 10분). 사람이 노션을 고치면 다음 cron 이 덮어씀.
2. **스키마가 사람 손에 있음**: 속성 이름·유형이 코드에 고정 → 이름을 바꾸거나 DB 를 잘못 연결하면 cron 이 매번 실패(11-09 「Could not find property 상태」, 연결 시 검사로 막음 #1344).
3. **연결 절차 부담**: 내부 통합 생성(소유자만) → 페이지 연결 → 토큰 저장(MFA) → DB 링크 2개. 11-08~09 동안 3번 막힘(연결 메뉴 미노출·토큰 파일·DB 뒤바뀜).
4. **다른 고객 확장 불가**: 고객마다 노션이 있어야 하고, 내부 통합 방식이라 공개 OAuth 앱 심사가 별도로 필요(설계 §9 「P2 이후」).
5. **변환 손실**: 노션 블록 → 평문 변환(표·토글·하위 페이지 깊이 3 제한), 노션 이미지 1시간 만료라 사진은 드라이브로 분리.
6. **코드량**: 노션 전용 코드 약 600줄(`notion.ts`·`notion-schema.ts`·`notion-blocks.ts`·`intake.ts` 수신/취소/projection·`request-create.ts`)과 cron 1개.

노션의 장점: 팀이 이미 쓰는 편집 환경(자유 서식·모바일·댓글), 소재와 업무 문서가 한 곳.

## 3. 선택지

| 안                                            | 내용                                                                                      | 장점                                                                                                    | 단점                                 |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| ① 현행 유지                                   | 노션 원본 + 에밀리 `sc_request_post`                                                      | 추가 개발 없음                                                                                          | §2 비용 그대로, 다른 고객 확장 불가  |
| **② Workdeck 원본 + 노션은 선택 연결 (추천)** | 소재·요청을 Workdeck 에서 만들고 편집. 노션은 「가져오기 채널」로만 남김(연결한 Space 만) | 노션 없는 고객도 바로 사용, 상태 지연·스키마 고장 없음, 기존 파이프라인(정규화·사진·승인) 그대로 재사용 | 소재 편집·요청 화면 신설             |
| ③ 노션 완전 제거                              | ②에서 노션 코드 삭제                                                                      | 코드 최소                                                                                               | 팀의 노션 작성 습관을 바로 끊어야 함 |

②를 추천한다. 정규화·근거 검증·사진 동기화·제안·승인·Aside 게시는 **소재 출처와 무관하게 이미 동작**한다. 바꿀 곳은 「입력」(소재·요청 생성)과 「보기」(요청 목록)뿐이다. ③은 ②가 자리 잡은 뒤 노션 사용량을 보고 정해도 늦지 않다.

## 4. ② 단계 계획

### Phase 1 — 데이터 모델 (마이그레이션 1개, additive)

- `ScSource.origin` (`WORKDECK` | `NOTION`), `notionPageId` nullable, 본문 `body Json`(TipTap doc) 추가. 저장 시 기존과 같은 방식(평문 → 해시 → 같으면 버전 재사용, 다르면 정규화·근거 검증 → 새 버전).
- `ScPublishRequest.notionPageId` nullable, `origin` 추가. 노션 projection 은 `notionPageId` 있는 요청만.
- 유일 제약 `(spaceId, notionPageId)` 는 null 허용이라 그대로 둔다.

### Phase 2 — 「발행 요청」 화면 (세일즈 콘텐츠 사이드바 새 항목)

- 목록: 제목·소재·유형·희망일·**상태 배지**(노션 9단계와 같은 라벨, `notionStatusFor` 재사용)·다음 할 일 링크(승인 대기 → 승인 화면, 사진 대기 → 배포).
- 「새 요청」: 소재 선택 → 유형·관점·희망일 → 저장 즉시 처리(`sc_request_post` 와 같은 함수).
- 상세: 진행 단계·막힌 이유(`lastError`)·결과 링크·「다시 요청」·「취소」(승인 전만).

### Phase 3 — 「소재」 화면

- 목록·편집: 항목 필드 + 본문(기존 TipTap 에디터 재사용) + **드라이브 폴더 선택**(허용 공유 드라이브 안 폴더 목록 — SA 로 조회).
- 사진 그리드: AI 설명·얼굴 판정 표시 + **얼굴 사진 수동 허용 토글**(남은 개발 2-2 를 여기서 흡수, `allowedByUserId/At/Md5` 이미 있음).
- 저장 시 버전 생성 + 「이 소재로 글 요청」 버튼.

### Phase 4 — 에밀리

- `sc_request_post` 가 노션 미연결 Space 에서는 Workdeck 에 직접 요청 생성.
- `sc_create_source`: 슬랙으로 받은 행사 메모·사진 → 소재 생성 + 사진 드라이브 업로드(설계 결정 9). 드라이브 **쓰기** 권한이 필요해 SA 스코프 확장(drive.file) 검토.

### Phase 5 — 노션 정리 (사용량 보고 결정)

- 노션 연결 Space 가 0 이거나 팀이 Workdeck 화면으로 옮기면 cron·노션 코드 제거(③).

규모 감: Phase 1 반나절, Phase 2 1~1.5일, Phase 3 1.5~2일(폴더 선택·사진 그리드), Phase 4 1일+(드라이브 쓰기 권한 검증 포함).

## 5. 결정이 필요한 것

1. **팀이 소재를 계속 노션에 쓸지** — 쓴다면 Phase 3 우선순위를 낮추고 Phase 2(요청 화면)부터.
2. **다른 고객에게 이 기능을 열지** — 연다면 ② 필수(노션 없는 고객).
3. **모바일 입력 필요 여부** — 현장(행사장)에서 사진·메모를 바로 올리려면 Phase 4(슬랙 → 에밀리)가 웹 화면보다 빠른 해법.
4. 노션 기존 소재 2건(조민주 협업 1·2)은 Phase 1 이후에도 `origin=NOTION` 으로 그대로 동작 — 이관 불필요.

## 6. 추천 순서

Phase 1 → Phase 2(요청 화면) → Phase 3(소재 화면 + 얼굴 허용) → Phase 4. 노션은 당분간 병행.
화면 작업(2·3)은 착수 전에 `ui-plan` 으로 와이어프레임 승인을 받는다(새 화면 규칙).
