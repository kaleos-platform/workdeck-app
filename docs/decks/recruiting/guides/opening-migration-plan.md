## 2026-09-30 날짜 숫자 항목과 표시 속성 지원

이번 변경은 누적 모집 관리 앱 개선과 함께 **로컬 미커밋 코드**에 반영했다. 이 절이 아래 초기 설계의 number/date 미지원 상태보다 최신이다. 운영 배포와 실제 이전은 하지 않았다.

- 공고 저장 스키마·편집기의 타입 선택·미리보기·이전 변환기에 number/date를 추가했다. 공개 폼은 이미 입력 타입을 렌더링하고 있었으므로 타입을 문자열로 강제 변환하는 방식으로 우회하지 않았다. 숫자 입력은 소수 입력을 위해 step=any를 사용한다.
- `description/placeholder`는 저장 스키마, 편집기 시딩/저장, 이전 변환기에 보존한다. 설명은 공개 폼과 미리보기에 표시한다. 편집기에서 별도 설명 수정 UI를 추가한 것은 아니다. 길이 제한·자유입력 선택·파일 제한 등 다른 속성은 계속 `UNSUPPORTED_ATTRIBUTE`로 보류한다.
- `form-values.ts`의 공통 검증을 공개 클라이언트·공개 API·이전 변환기에서 사용한다. 날짜는 실제 존재하는 YYYY-MM-DD를 확인하며 2월 30일 자동 보정을 허용하지 않는다. 숫자는 유한한 십진수/지수 표기 문자열을 허용하고 NaN/Infinity/16진수/쉼표 형식은 거부한다. 원본 문자열의 표기는 그대로 유지한다.

- 이전의 숫자 JSON 값은 유한하고 안전한 경우 문자열로 변환한다. 안전한 정수 범위를 벗어나는 JS number는 이미 정밀도를 잃었을 수 있어 차단한다. 날짜·숫자 타입을 name/phone/email/address 같은 표준 PII key에 연결한 폼은 보류한다.
- 과거 폼 근거: `opening_api/src/app/posting/update_posting.ts`는 application_entries를 현재 posting 행에 덮어쓴다. 확인한 모델 파일에서 전용 폼 이력 모델을 찾지 못했다. 이것은 백업·외부 로그가 없다는 증거가 아니다. 현재 폼이나 posting.updated_at만으로 과거 snapshot을 확인했다고 표시하지 않는다. 선택값 의미 변경은 label/type 일치만으로 검출할 수 없으므로 `sourceSnapshotVerified` 요구는 유지한다.

## 2026-09-30 폼과 제출값의 순수 변환기

[`opening-form-migration.ts`](../../../../src/lib/hiring/opening-form-migration.ts)에 M2의 첫 범위를 구현했다. DB 조회/쓰기, 파일 복사, 알림, PII 암호화는 실행하지 않는다. 아직 이전 CLI·앱 요청 경로에 연결하지 않았다.

- `planOpeningForm(sourceSnapshotRef, source)`는 출처 스냅샷 참조와 폼 정의를 받는다. 표준 PII key는 유지하고 나머지는 출처+원본 key/type/label의 hash로 `custom_*` ID를 만든다. 같은 출처/정의는 배열 순서와 관계없이 ID가 같으며 다른 출처는 분리한다. 원본이 바뀌면 새 snapshot과 별도 대응표가 필요하다.
- 같은 key라도 type/label이 다르면 구분할 수 있지만, 동일 식별 조합이 반복되거나 표준 PII key가 중복되면 차단한다. key/label 누락, 미지원 타입, 설명·자유입력·제약 등 현재 보존하지 못하는 속성은 성공 결과에서 제거하지 않고 오류로 반환한다.
- select/multiselect의 원본 선택값을 표시 라벨로 변환한다. 원본 숫자 1과 문자열 "1"은 구 서비스 비교 방식에 맞춰 같은 토큰으로 보되, 둘이 별개 선택지로 공존하면 모호하므로 차단한다. 표시명 중복·빈 선택값·알 수 없는 선택값도 차단한다.
- `convertOpeningSubmission(plan, source, { sourceSnapshotVerified: true })`는 호출부에서 **제출 당시 폼 대응을 확인한 경우에만** 사용한다. 이 boolean은 증거를 자동 검증하는 기능이 아니다. 단순히 현재 폼을 읽었다는 이유로 true를 설정하지 않는다. 원본 key/type/label이 정확하게 대응되어야 하며 과거 폼 이력과 수동 확인의 영속 기록은 아직 미구현이다.
- 제출의 중복 항목, 미매칭 항목, 빈 필수값/필수항목 누락, 잘못된 값 형태, 자유입력 선택값, 미이전 파일은 전체 결과를 실패로 반환한다. 일부 성공 데이터를 함께 반환하지 않는다. 오류에는 코드와 배열 위치만 넣고 원문 값·라벨·PII를 넣지 않는다.
- 성공 반환값은 평문 PII를 포함할 수 있는 메모리 중간값이다. 로그/JSON 리포트로 출력하지 않고 이후 적재 단계에서 `buildApplicationPii`를 적용해야 한다. 커스텀 항목의 민감정보 정책과 파일 key 매핑도 별도로 필요하다. 계획의 Map은 메모리용이며 영속 이전 원장을 대신하지 않는다.

합성 테스트 15개로 안정적인 ID, 중복 custom 구분, 선택값/다중선택, 모호한 필드/선택지, 과거 폼 미확인, 잘못된 값과 파일 처리 보류를 검증했다. 운영 지원서 원문을 변환기에 전달하거나 적재하지 않았다. number/date와 추가 속성을 실제로 지원하는 일, 과거 폼의 증거 확보, 영속 ID 대응, 파일·PII 적재 연결은 남아 있다.

## 읽기 전용 검사기 실행

[`audit-opening-migration.mjs`](../../../../scripts/audit-opening-migration.mjs)는 고객 ID를 명시한 범위만 집계한다. 전용 파일의 `DATABASE_URL`을 사용하며 Workdeck `.env.local`을 자동으로 읽지 않는다. 아래 ID는 예시이며 실제 대상 고객 ID로 바꾼다.

```bash
node scripts/audit-opening-migration.mjs --help
OPENING_ENV_FILE=/secure/opening.env node scripts/audit-opening-migration.mjs --spaces 101,202
node --test scripts/__tests__/audit-opening-migration.test.mjs
```

- 연결부터 기본 read-only를 설정하고 REPEATABLE READ READ ONLY 트랜잭션으로 집계한 뒤 ROLLBACK한다. 쿼리당 30초 제한, lock 3초 제한을 둔다. 고객 1~100개를 허용하고 존재하지 않는 고객이 섞이면 실패한다. ID는 BIGINT 문자열로 전달한다.
- 출력은 합산된 건수이며 고객 ID·폼 라벨·제출값·연락처·파일 key를 포함하지 않는다. 여러 지표에 같은 행이 잡힐 수 있으므로 지표 합계는 이전 차단 행 수가 아니다. 숫자는 PostgreSQL count 정밀도를 유지하는 문자열이다.
- 범위: 공고 상태/담당자 이메일 존재/JSON 구조, 공고·지원서의 누락·중복 key/타입/선택지/추가 제약, 근무조건 존재, 지원서 동의/상태/공고 관계, 지원서에 연결된 첨부 파일의 메타데이터 상태. 근무조건은 false/0도 명시적 값이면 검토 대상으로 잡는 보수적인 존재 검사다.
- 미검사: 콘텐츠 섹션 전체 변환, 공개 이미지·scene 참조, 고아 첨부의 고객 귀속, S3 실재·바이트, 계정·권한·결제, 과거 폼과 제출값 대응, 대상 적재. 리포트의 `unverified`와 이 목록을 함께 확인한다. 기준 테이블 `posting/application`의 JSON 구조와 모델 필드를 가정하므로 실제 운영 스키마가 다르면 성공으로 간주하지 않고 실패한다.
- 종료 코드: `0`은 검사 범위에서 플래그 없음(이전 승인 아님), `2`는 검토 필요, `1`은 검사 실패. 오류 원문은 접속/개인정보 노출 방지를 위해 출력하지 않는다. 실패 시 부분 집계 결과를 출력하지 않는다.
- 기본 테스트는 연결 없이 실행하고 SQL 테스트 1개를 skip한다. `AUDIT_TEST_DATABASE_URL`을 별도 지정하면 합성 CTE만 사용해 PostgreSQL SQL 테스트까지 실행한다. 실제 테이블 조회·생성·수정은 하지 않는다. 개발용 연결에서 합성 SQL 테스트 6개가 통과했다. 운영 고객 읽기 전용 실행 결과는 위 2026-09-30 기록을 따른다.

## 판단

모집 관리 단일 deck 안에서 고객을 이전하는 방향은 현재 업무와 맞는다. 공고 제작 고객을 먼저 검증하고, 지원자 관리 고객은 별도 검증 단계로 진행한다. 그러나 현재 모델에 데이터를 그대로 복사하면 정보와 동작이 일부 달라진다. 아래의 미대응 항목을 처리하기 전에는 전체 이전이나 opening.work 종료를 완료로 판단하지 않는다.

근거는 `opening-ref/opening_api/src/models/`와 Workdeck `prisma/schema.prisma`, 폼 검증·PII 처리 코드다. 운영 데이터 규모는 [2026-09-11 읽기 전용 집계](../../../audit/2026-09-11-opening-db-analysis.md)에 한정한다. 당시 공고 4,030건, 지원서 5,411건, 파일 메타데이터 50,427건은 **전체 원본 규모**이며 최종 이전 건수가 아니다. 이번 작업에서 운영 DB·S3·결제 원장은 재조회하지 않았다.

## 3. 현재 확인된 이전 차단 항목

### 폼과 제출값

- opening 폼의 `number/date`는 현재 `formFieldTypeEnum`에 없다. string으로 바꾸면 입력 검증과 UX가 달라진다. 사용 건수를 먼저 집계한 뒤 타입 지원 또는 합의한 변환을 선택한다.
- opening 선택지는 `{label,value}`이고 Workdeck은 문자열 `options`다. 값과 라벨이 다르면 제출값을 포함해 양방향 대조해야 한다. 자유입력 옵션, 설명, placeholder, 길이/파일 제한은 현재 폼 스키마에서 직접 대응되지 않는다.
- opening의 여러 항목이 `key=custom`일 수 있다. Workdeck의 제출값/엑셀은 key를 식별자로 사용하므로 그대로 옮기면 충돌한다. 폼별 안정적인 `custom_*` 키와 원본 항목 대응표가 필요하다. 같은 label, 과거 폼 수정, key 누락으로 대응이 모호하면 추측하지 않고 차단한다. 현재 폼 배열 인덱스만으로 과거 제출값을 연결하지 않는다.
- 표준 key가 없고 라벨만 있는 이름/전화 항목은 승인된 규칙으로 식별한 뒤 PII 유틸에 전달한다. 구 HMAC을 복사하지 않는다. 표준 PII 값이 JSON에 남지 않는지 검증한다. 커스텀 문항에도 개인정보가 있을 수 있으므로 원문 전체를 로그/보고서에 출력하지 않는다.
- `required_privacy_agreed_at`은 `privacyAgreedAt`에 대응 가능하지만 `optional_privacy_agreed_at`은 전용 대상 필드가 없다. 별도 제한 접근 보존 또는 스키마 확장 결정이 필요하다. 필수 동의로 합치거나 새 동의 시각을 만들지 않는다.

### 공고와 편집 정보

- `posting_title/company_intro/description/detail_text`, 담당자 email에는 일대일 전용 필드가 없는 항목이 있다. 렌더링 가능한 블록으로 변환하거나 제한 접근 원장에 보존할지 항목별로 결정한다. 원문 JSON 보관만으로 화면에서 사용할 수 있다고 판단하지 않는다.
- `posting_position`의 변동근무, 협의시간, 커스텀 요일/시간, 수습/계약 개월, 모집인원 미정 등의 의미가 현 모델의 단순 필드와 다르다. 대상 고객 사용 건수를 보고 필수 필드 확장 또는 명시적 텍스트 보존을 결정한다. 빈 값으로 버리지 않는다.
- content에 DB `data`와 별도 `file_key`가 함께 존재한다. 실제 편집기가 사용하는 최신 scene의 출처와 버전을 대조한다. PNG만 옮기면 편집 기능을 보존한 것이 아니다.
- 템플릿/콘텐츠 비활성 항목과 삭제 공고는 대상 모델의 보관 상태가 동일하지 않다. 복구 요구와 이전 범위를 확정한 뒤 제외 사유를 원장에 남긴다.

### URL·계정·결제

- 같은 uuid를 유지해도 `opening.work/p/...` 도메인은 저절로 유지되지 않는다. 기존 도메인의 전달 계층과 실제 경로별 응답 정책이 필요하다. 구 알림 URL은 인증 토큰 체계도 별도 확인한다.
- 외부 채용사이트에 이미 붙여넣은 HTML은 이전 후 자동 수정되지 않는다. 기존 이미지/CDN 주소를 유지하거나 같은 주소에서 새 객체를 제공해야 한다. 현재 HTML 생성 코드 변경만으로 기존 게시물을 보호할 수 없다.
- 기존 admin을 일괄 OWNER로 승격하지 않는다. 계정 인증 연결과 소유자 지정이 확인되지 않은 Space는 전환 대상에서 보류한다.
- 기존 결제 상태는 Workdeck 구독 상태와 일대일이 아니다. 취소예정·미납·갱신중 고객의 잔여 권리와 청구 주체를 먼저 확정한다. 이 문서는 결제 사업자 이관 가능 여부를 확인한 결과가 아니다.

## 4. 기존 스크립트의 재사용 범위

[`scripts/migrate-opening-templates.ts`](../../../../scripts/migrate-opening-templates.ts)는 `setting.detail_template_samples` 기반 **글로벌 샘플 전용**이다. 고객 Space·계정·공고·지원서·구독 이전 도구로 사용하지 않는다.

- 재사용 후보: 섹션별 계획 생성, S3 scene/PNG 읽기, 이미지 업로드, `sourceRef` 대응 개념.
- 고객 이전에 그대로 사용하면 안 되는 부분: `spaceId=null/isSample=true`, 공고 동적 섹션 생략, 기본 custom 생략, 기존 contents 교체, 쓰기가 기본이고 `--dry-run`이 선택인 실행 방식.
- 기존 dry-run은 DB 참조 중심이다. 객체 실재·다운로드·복호화·고객별 무결성 검증 완료를 의미하지 않는다. 코드에 read-only 세션 강제도 별도 적용해야 한다.

## 5. 이전 도구 계약 — 다음 구현 대상

현재 고객 이전 CLI는 구현되지 않았다. 다음 인터페이스는 **설계안**이며 실행 가능한 명령으로 제공하지 않는다.

1. 기본 모드는 읽기 전용 검증. source DB는 읽기 전용 트랜잭션과 시간 제한을 사용한다. 대상은 운영/개발 연결과 분리한 이전 검증 전용 환경으로 명시한다. 운영 데이터를 평소 개발 DB로 복사하지 않는다.
2. 고객 allowlist와 원본 snapshot 시각을 고정한다. 범위 없는 전체 이전을 기본값으로 두지 않는다. 파일은 해당 고객의 참조 closure에서 선정한다.
3. plan에 원본 스키마 버전, 변환기 버전, 고객 범위, 소스 식별자, 대상 식별자, 변환 종류, 제외/차단 사유, 이전/검증 상태를 기록한다. 인증정보·PII·서명 URL·결제 토큰은 기록하지 않는다. ID 자체도 제한 접근 산출물로 취급한다.
4. 매핑 키는 `(sourceSystem, sourceTable, sourceId, occurrence)`다. BIGINT는 문자열로 다뤄 JavaScript 정밀도 손실을 피한다. occurrence는 같은 content를 여러 섹션에서 사용하는 경우 필요하다. 대상 ID는 최초 계획에서 발급하고 영속 원장에 기록해 재실행 시 재사용한다.
5. 템플릿 외 다수 대상 모델에는 `sourceRef`가 없다. 이전 원장은 검증 환경에서 먼저 설계·구현한다. 메모리 Map이나 임시 파일만으로 운영 멱등성을 주장하지 않는다. DB 행 생성과 매핑 확정의 원자성을 보장할 수 있는 원장 저장 방식을 결정한다. 스키마 확장 시 Prisma migration을 사용한다.
6. 동일 snapshot 재실행은 생성 0건이 기준이다. 이미 사용자가 수정한 대상 행은 자동 덮어쓰지 않고 충돌로 보고한다. 원본이 변경된 경우 별도 delta 계획을 만든다.
7. DB 트랜잭션과 객체 저장소 복사는 분리한다. 결정된 객체 키·내용 checksum·업로드 상태를 원장에 남기고 파일 실패 후 이어서 실행한다. DB rollback이 업로드 파일을 지웠다고 가정하지 않는다.
8. 검증 모드는 알림·메일·결제·공개 접수·관련 스케줄러의 외부 부작용을 차단한다. 운영 전환만이 의도적으로 이 기능을 활성화한다.

## 6. Dry-run 보고서와 통과 기준

원본 → 계획 → 검증 환경 적재의 세 단계를 구분한다. 읽기 전용 분석만 수행한 결과를 ‘이전 완료’라고 표시하지 않는다.

| 검사        | 통과 기준                                                                                                                                                                                             |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 범위/건수   | 원본 대상 = 이전 계획 + 명시적 제외 + 차단 건수. 테이블·Space·상태별로 대조하며 unexplained 차이 0건. 변환으로 행 수가 늘어나는 블록/PII는 별도 계산.                                                 |
| ID/관계     | 중복 대응 0, 미해결 FK 0, Space 교차 연결 0, uuid 충돌 0. 작성자 미매칭을 알 수 없는 사용자로 임의 치환하지 않음.                                                                                     |
| 상태/시각   | 허용하지 않은 상태 0. 삭제/취소/마감/동의 시각 손실 0. timezone 경계 합성 사례 통과.                                                                                                                  |
| 폼/제출값   | 필드 key 중복 0, 해석 불가능한 선택값 0, 누락 항목 0. 폼이 바뀐 과거 지원서도 값/라벨 보존.                                                                                                           |
| PII         | 합성 경계 테스트 및 허용된 검증 과정에서 복호화 round-trip 일치. JSON/로그에 표준 PII 평문 없음. 정규화된 동일 전화번호의 중복/블랙리스트 매칭 일치. 원문이나 평문 SHA를 공개 리포트에 저장하지 않음. |
| 파일        | 참조 파일 누락 0, MIME/크기/실제 내용 확인, source/target checksum 일치. S3 ETag를 무조건 파일 checksum으로 간주하지 않음. private 첨부의 익명 접근 거부 확인.                                        |
| 콘텐츠      | 섹션 순서·제목·링크·이미지 보존, scene 편집→저장→HTML 확인. 동적 섹션과 미지원 항목의 무고지 삭제 0.                                                                                                  |
| 공개 URL    | 기존 게시물의 이미지 URL과 공고 링크가 계획대로 응답. 마감/삭제 공고에서 접수 재개 없음. 실제 서비스 전환 전 테스트 경로로 확인.                                                                      |
| 권한        | OWNER/ADMIN/MEMBER 및 다른 Space/로그아웃 조합으로 접근 확인. 유효하지 않은 계정 연결 0.                                                                                                              |
| 재실행/중단 | 동일 계획 2회째 신규 생성 0. 파일 실패/DB 실패 후 재개 성공. 고객 편집 충돌을 덮어쓰지 않음.                                                                                                          |
| 결제/알림   | 검증 실행의 실제 청구·취소·알림 발송 0. 운영 전환 원장은 고객별 잔여 기간과 청구 주체 대조 완료.                                                                                                      |

요약 보고서는 `runId`, `sourceSnapshotAt`, `transformVersion`, 범위 집계, entity별 source/planned/excluded/blocked/imported/verified 수, 오류 코드별 건수, 파일 검증 요약, 재실행 결과를 포함한다. 차단이 있으면 실패 종료한다. 상세 원장은 제한 접근 저장소에 보관하고 Git에는 합성 예시와 집계만 남긴다.

## 7. 전환 순서와 복귀 기준

1. 읽기 전용 사용 분포 확인: custom/date/number·미대응 근무조건·삭제 상태·파일 참조 유형별 건수. 대표 고객은 공고 제작 중심, 지원자 관리 중심, 다매장 유형에서 선정한다.
2. 합성 데이터 검증: 변환·관계·PII·재실행 실패 사례를 먼저 구현한다.
3. 제한된 검증 환경: 선정 고객 범위를 고정해 적재/대조한다. 대상 원본을 수정하지 않는다.
4. 고객 검수: 공고 재사용→HTML 복사, 지원서 열람→상태 변경→내부 코멘트→첨부/엑셀 흐름을 확인한다. 사람인·알바몬 편집기의 결과도 별도로 확인한다.
5. 전환 시점: 최종 snapshot/delta와 동결 시작·종료 시간을 기록한다. 웹 편집뿐 아니라 익명 지원 접수·파일 업로드·worker·webhook 쓰기도 다룬다. 한쪽만 쓰기 주체가 되게 하고 누락 기간을 만들지 않는다.
6. 관찰 기간: 기존 도메인/파일 제공을 유지하며 고객별 문의·파일 404·접수 오류·건수 불일치를 확인한다. 기간 수치는 아직 미확정이다.
7. 종료: 모든 고객의 전환/미전환 처리가 결정되고, 결제 원장 대조 및 구 URL/파일 보존 책임이 확정된 뒤 결정한다. 소스 데이터와 스토리지는 별도 보존 정책 없이 삭제하지 않는다.

전환 전에 실패하면 구 서비스를 계속 사용한다. 전환 뒤 Workdeck에 신규 접수·편집이 생겼다면 단순 DNS 복귀는 데이터 손실을 만들 수 있다. 그 시점에는 새 쓰기를 통제하고 delta 회수·대조 후 복귀하거나 Workdeck에서 복구한다. 역방향 보존이 검증되지 않았으면 무손실 rollback이 가능하다고 표현하지 않는다.

## 8. 다음 작업 단위

- M1: 원본의 미대응 항목 사용 분포를 집계하는 읽기 전용 검사기와 합성 fixture.
- M2: 상태·폼 key/선택값·콘텐츠 계획 변환기. 미지원 데이터는 누락시키지 않고 차단 리포트.
- M3: 계정/Space 확인 및 영속 ID 원장·파일 복사·재개/충돌 처리 설계와 검증 환경 구현.
- M4: 대표 고객 dry-run 및 HTML/지원자 기능 검수. 계정·원본 파일·전환 정책이 확인되어야 하는 단계.
- M5: 결제/URL/접수 동결·delta·복귀 절차 검증 후 순차 전환.
