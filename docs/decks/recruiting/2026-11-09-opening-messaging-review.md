## 결론 요약

1. **모집 관리 deck에 알림톡·문자 기능은 12/18 전에 만들지 않는다(권고: 불필요).** 오프닝 이전 고객이 잃는 것은 "지원 접수 완료" 알림톡(지원자)과 "어제 새 지원자 N명" 일일 알림톡(담당자) 두 가지뿐이다. 최근 발송량은 아주 적다. 법인이 달라 발신프로필·발신번호를 넘겨받을 수 없고, 채용 deck은 신규 기능 동결 상태다.
2. **A안(종료만)으로 가면 이 검토는 의미가 없다.** B안(이전)일 때만 간소안을 백로그에 올린다. 간소안은 담당자 "지원 알림" 토글(현재 저장만 되고 동작 없음)을 이메일 일일 요약으로 연결하는 것이다.
3. **메일에서 오프닝 종료일(12/18)보다 먼저 오는 기한 2건을 발견했다.**
   - 카카오 「오프닝(@오프닝)」 채널: 휴면 상태라 **11/12 프로필 삭제** 예정
   - 솔라피 발신번호: **11/13 10:00 만료** 예정

   오프닝 코드가 알림톡 요청에 넣는 발신번호가 이 만료 번호와 같은 패턴(앞 5자리·끝 2자리 일치)이다. 그대로 두면 오프닝의 남은 알림톡(접수 안내·일일 요약)이 **12/18 전에 끊길 수 있다**. 둘 다 "유지할지, 끊기도록 둘지"는 사용자 결정 사항이다.

## 2. 오프닝 메시지 기능 실사용 (코드 분석)

### 채널과 벤더

- **카카오 알림톡**: `src/lib/alimtalk_api.ts`가 자체 AWS Lambda로 POST하고, 실제 벤더 호출은 Lambda 안에 있다(저장소 밖). 페이로드 `{to, from, kakaoOptions:{pfId, templateId, variables}}`와 ID 접두어가 **솔라피 형식**이다. 위 솔라피 발신번호 메일과도 일치해 벤더는 솔라피로 본다.
  - 발신번호는 코드에 하드코딩, 부스팅용 pfId도 하드코딩(2종).
  - 나머지 템플릿 ID·pfId는 DB `setting` 테이블에만 있다.
- **이메일**: Mailgun(`src/lib/mailgun_api.ts`). 고객사 관리자·멤버에게만 보낸다(가입·초대·체험/구독 만료·종료 고지).
- **SMS**: 서버 발송 없음. 사장의 「자주 쓰는 메시지」는 `sms:` 딥링크로 **사장 본인 폰 문자앱**을 연다. 서버 과금 없음.
- **Slack**: 내부 모니터링만.
- 친구톡·웹푸시: 없음.

### 실사용량 (기존 자료 범위)

- 운영 DB 감사(`docs/audit/2026-09-11-opening-db-analysis.md:25-26`)
  - `alimtalk` 기록 **9,971건**, 최근 생성 2026-09-10 → 감사 시점에도 발송 중.
  - 결과 안내 `application_notification` **97건**, 최근 2023-10-28 → UI 비활성화(2023-11-01) 직전에 멈춤. 코드 분석과 일치한다.
- 최근 규모: 최근 90일 지원서 **193건 / 4개 Space**(같은 문서 :13-21).
  - 접수 알림톡은 지원서당 최대 1건이라 **월 ~65건 이하**.
  - 일일 요약은 담당자당 하루 최대 1건이다(새 지원이 있는 날만).
  - 위 추정은 운영 DB 재조회 없이 기존 수치로 잡은 상한이다. 금액도 건당 수십 원 수준이라 월 수천 원 이하로 **추정**한다.
- 솔라피 잔액·충전·사용량 안내 메일은 3개월 내 없음 → 실제 발송액은 메일로 확인할 수 없다. 이 결론을 내는 데 **운영 DB 실측은 필요 없다고 판단**했다.

## 4. 알림톡·문자 기능 필요 여부 판단

| 비교 항목 | 내용 |
|---|---|
| 이전 고객 의존도 | 낮다. 실사용은 자동 2종(접수 안내·일일 요약)뿐이고, 수동 결과 안내는 2023년 11월부터 꺼져 있다. 최근 90일 지원이 있는 공간은 4곳 |
| 대체 수단 | 접수 안내 → 제출 완료 화면(이미 있음). 일일 요약 → 담당자 이메일 요약(`notificationEnabled` + Resend). 결과 안내 → 기존 열람 링크 수동 전달(오프닝 현행과 동일 수준) |
| 구현 범위 | 솔라피(또는 대행사) 계약·키 관리, **의식주의 명의 카카오 채널·발신프로필 신규 등록**, 발신번호 등록·인증, 알림톡 템플릿 신규 작성·심사, 발송 로그·실패 처리, 수신자 번호 복호화 경로, 고객별 on/off |
| 비용·과금 주체 | 오프닝은 운영사 전액 부담·고객 청구 없음. 워크덱은 토스 계약 지연으로 구독 결제가 중지 상태(`BILLING_CHECKOUT_PAUSED`)라 건당 과금 불가 → 워크덱 부담 |
| 법적 이슈(확인 항목, 확정 아님) | ① 법인이 다르다(피크페이 vs 의식주의). 피크페이의 채널·발신프로필·발신번호·템플릿은 이전할 수 없어 전부 새로 등록해야 한다 ② 알림톡은 정보성이라 광고 수신동의 대상은 아니지만, 지원자 전화번호를 발송 대행사에 넘기므로 개인정보 처리위탁 고지(처리방침)가 필요한지 확인 ③ 워크덱이 지원자 개인정보의 수탁자 지위인지 정리 필요 |
| 12/18 전 가능 여부 | 사실상 불가. 채널 개설·템플릿 심사 소요에 이전 신청 마감(12/11)까지 겹치고, 채용 deck 신규 기능 동결 결정(10-29)과도 충돌 |

**권고: 불필요(12/18 전 미구현).** 근거는 위 표 전체. 조건부 후속은 다음과 같다.

- **A안(종료만)**: 이전 고객이 없으므로 할 일 없음.
- **B안(종료+이전)**: 이전 안내에 "워크덱은 알림톡 대신 제출 완료 화면 + 결과 링크 전달 방식"이라고 차이를 명시한다. 이전 고객이 요청하면 간소안(담당자 이메일 일일 요약)을 동결 예외로 검토한다. 이 경우 recruiting 지원 접수 경로에서 `notificationEnabled`를 읽고 Resend로 담당자에게 보낸다. 지원자 대상 발송은 만들지 않는다.
