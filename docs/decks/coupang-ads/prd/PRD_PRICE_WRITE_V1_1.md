# PRD — 쿠팡 Open API 가격 쓰기 v1.1 (개정)

**작성** 2026-10-05 · **개정** 2026-10-09(실사용 피드백 반영 — §12) · **Deck** coupang-ads (진입점 seller-hub 가격시뮬) · **상태** 운영 배포·실사용 검증 완료 · **선행 문서** [`PRD_PRICE_WRITE_V1.md`](./PRD_PRICE_WRITE_V1.md)

> 이 문서는 v1 스펙을 **덮어쓰는 차분**이다. 여기 적힌 절은 v1 의 같은 주제를 대체하고, 적히지 않은 절(§3 쓰기 축, §5 가격 매핑·VAT·10원, §7.4 현재가 가드 없음, §8 Wing 딥링크, §10 응답 파싱, §11 실패 유형, §14 운영 함정)은 v1 그대로 유효하다.

## 0. 왜 개정하나 — 효용 검토 결과 (2026-10-05)

v1 구현 완료 후 "정말 필요한가"를 사용자 인터뷰로 다시 검토했다.

- **필요하다.** 사용자는 주력 상품 가격을 **매주 1회 이상** 가격시뮬에서 계산하고(시나리오로 저장하지 않고 화면만 보고 씀 — 저장 시나리오 9건은 사용량 과소 지표), Wing 에서 **옵션 여러 개 × 2채널의 판매가 + 자동조정 최저가**를 매번 손으로 다시 입력한다. 10칸 이상 수작업이고, 최저가 오입력은 역마진 판매로 이어진다.
- 그러나 v1 흐름은 이 사용자에게 맞지 않는 부분이 있었다 — 1인 운영인데 승인 큐를 두 번 거치고, 세트 가격을 단품에 쓸 수 있는 사고 경로가 있고, 매칭이 반영 순간마다 수동이었다.

## 2. D1 — 승인 큐 제거

**근거**: 요청자=승인자=1인. 미리보기가 이미 "무엇이 얼마로 바뀌는지"를 보여주므로 승인은 같은 확인의 반복이다.

- 신규 `POST /api/sh/coupang-price/apply` — 미리보기와 같은 입력을 받아 **서버에서 대상·가드를 다시 계산**하고(클라이언트가 보낸 타깃을 믿지 않는다) `CoupangWriteJob{kind:PRICE_CHANGE, actionId:null}` 를 만든다. 응답 `{ jobId }`.
- **중복 실행 가드**: 같은 space 에 `PRICE_CHANGE` 잡이 `PENDING|RUNNING` 이면 409. 더블클릭·연타 방지. (가격 PUT 은 자연 멱등이라 결과는 같지만 잡이 두 개 쌓이면 다이얼로그 결과가 헷갈린다.)
- 권한: seller-hub deck 접근(`resolveDeckContext`) + **Space 역할 ADMIN 이상**. v1 은 승인 채널 구성으로 역할을 대신했는데(§12.1) 승인이 없어지면 API 자체에서 막아야 한다.
- v1 의 에이전트 액션 `coupang.price.change` 정의·Slack 결과 알림·승인 상세 시트 표시는 **삭제**한다. 승인 만료 게이트 수정(`4c28ba21`)은 공용 버그 수정이라 유지.
- 에이전트(MCP)가 가격을 제안하는 흐름은 비목표. 필요해지면 그때 승인 경로를 다시 붙인다(잡 생성부는 공용 함수로 둔다).

## 3. D2 — 다이얼로그 내 결과

- 신규 `GET /api/sh/coupang-price/jobs/[jobId]` — `{ status, results, error, createdAt, executedAt }`. space 스코프.
- 다이얼로그: 제출 후 "반영 중" 상태로 2초 간격 폴링, 최대 3분. 완료 시 옵션별 `성공 ₩X` / `실패: 쿠팡 메시지` 표.
- 다이얼로그를 닫아도 반영은 계속된다. 다시 열면(같은 채널 카드) **최근 잡 결과**를 보여준다 — 놓친 결과를 확인할 유일한 경로.
- 3분 초과 시 "워커가 아직 처리하지 않았습니다(워커 중단 의심)" 안내. stale 회수(v1 §16.3)는 그대로.

## 4. D3 — 자동조정 항상 켜기

- 쿠팡은 `apActive` 와 `apMinSalePrice` 를 함께 요구하고 현재 상태를 읽을 API 가 없다(v1 §9). 사용자는 주력 상품을 **전 옵션 자동조정 켜고 운영**한다.
- 따라서 반영은 항상 `apActive=true`, `apMinSalePrice = ceil10(recommendedRetail.min)`.
- 미리보기에 옵션별로 **"자동조정 켜짐 · 최저가 ₩X (최소마진 N%)"** 를 표시하고, 상단에 한 줄: "꺼져 있던 옵션도 자동조정이 켜지고, Wing 에서 정한 최저가는 이 값으로 바뀝니다."
- `apMinSalePrice < price` 가드(v1 §9.1)는 유지.

## 5. D4 — 워크덱 판매가 동기화

- 워크덱의 쿠팡 리스팅은 **판매자배송(MP) 채널에 1개**이고, 로켓그로스 채널은 대표 채널 리스팅을 미러링한다. 리스팅 1개에 쿠팡 가격 2개(RG·MP)가 대응한다.
- **규칙: MP 축 반영이 성공한 타깃만 `ProductListing.retailPrice = 반영가`.** RG 축 반영은 워크덱 판매가를 건드리지 않는다(RG 가격은 쿠팡에만 존재).
- 갱신 지점: 워커 `report` 라우트가 잡 결과를 기록하는 같은 트랜잭션.
- 실패 타깃은 갱신하지 않는다.

## 6. D5 — 세트 반영

가격시뮬의 상품 행(row) = `{ optionIds: string[], quantity }` (같은 가격의 옵션 묶음 × 수량). 행이 여러 개면 세트다.

**매칭 규칙 (일반화된 `deriveListings`)**: 리스팅 L 이 대상이려면

1. `L.items.length === rows.length`
2. `L.items` 와 `rows` 사이에 일대일 대응이 있어, 각 item 의 `optionId ∈ row.optionIds` 이고 `quantity === row.quantity`.

- 행 1개면 v1 과 동일(옵션별 단품 리스팅).
- 같은 상품 옵션 두 행(A그룹+B그룹 세트)도 같은 규칙 — 단품 리스팅은 item 수가 달라 절대 매칭되지 않는다. **v1 의 세트가→단품 사고 경로가 구조적으로 닫힌다.**
- 한 행의 `optionIds` 끼리는 같은 가격이므로, 조합(A1+B1, A2+B1 …)이 리스팅으로 여러 개 있으면 **모두 같은 가격으로 반영**한다.
- 대응 판정은 행 수가 작아(실측 최대 수 개) 백트래킹으로 충분하다.
- 가격시뮬 버튼 활성 조건: `mode === 'existing' && confirmedRows.length > 0`. v1 의 `isSingleProduct` 제한은 제거. 비활성 시 사유 툴팁(신규 상품 모드).
- 매칭 대상이 0개인 행 조합은 미리보기에 "판매채널 상품 없음"으로 표시(v1 `unmatched` 를 리스팅 단위로 일반화).

## 7. D6 — 일괄 매칭 + 자동 후보

### 7.1 자동 후보 경로

```
CoupangProductItem.rgVendorItemId
  = InventoryRecord.optionId (INVENTORY_HEALTH 최신 스냅샷)   ← vendorItemId=optionId (2026-09-07 실측, 전건)
  → InventoryRecord.skuId
  = InvLocationProductMap.externalCode (로켓그로스 위치)      ← 재고 대조용 사람 확정 매핑 415건(세트 29)
  → InvLocationProductMapItem[] {optionId, quantity}          = 구성
  → ProductListing (쿠팡 MP 채널, items 시그니처 일치)        = 후보
```

- 시그니처 일치 리스팅이 1개 → **후보**, 2개 이상 → **모호**, 0개 → **없음**.
- RG 축이 없는 MP 전용 쿠팡 옵션은 이 경로가 없다 → **수동**.
- 이미 `listingId` 가 확정된 항목은 후보 계산 대상이 아니다(사람 확정 우선, v1 원칙 유지).

### 7.2 화면 — seller-hub `판매채널 상품 > 쿠팡 매칭`

- 목록: 쿠팡 옵션(itemName · RG/MP 옵션ID · 쿠팡 현재가) | 상태(확정/후보/모호/없음/확인 필요) | 워크덱 리스팅.
- 상단 요약 + **"후보 N건 일괄 확정"** 버튼.
- 행 액션: 후보 확정 · 리스팅 직접 선택(기존 피커 재사용) · **연결 해제**(v1 에 없던 경로 — 잘못 확정한 매칭을 되돌릴 방법이 필요).
- **"지금 쿠팡 상품 불러오기"** — `PRODUCT_SYNC` 잡 수동 생성. v1 cron 의 20h 중복 판정은 cron 경로에만 적용(수동은 진행 중 잡만 막음). v1 후속과제 "cron 20h 창"을 여기서 해소.

### 7.3 확인 필요

일일 수집 후 다음은 "확인 필요"로 표시한다.

- 새로 나타난 쿠팡 옵션(미확정).
- 확정된 매칭인데 **자동 후보 경로가 다른 리스팅을 가리키게 된 경우**(재고 매핑·리스팅 구성이 바뀜).

### 7.4 반영 시점과의 관계

- 미리보기는 **확정 매칭만** 대상으로 쓴다. 후보·모호·없음은 "매칭 필요" 섹션에 표시하고, v1 의 지연 매핑 피커로 그 자리에서 확정할 수 있다(폴백 유지).
- 대상 리스팅의 쿠팡 항목이 `collectedAt` 기준 오래됐으면(v1 신선도 규칙) 경고.

## 8. D8 — 첫 운영 시험

1. 사용자가 주문이 적은 옵션 1개를 지정한다.
2. 그 옵션만 대상이 되는 가격시뮬에서 판매가를 현재가 ±10원으로 반영.
3. Wing 에서 판매가·자동조정 켜짐·최저가 확인.
4. 원래 가격으로 다시 반영(원복도 같은 경로로 검증).
5. 통과 후 주력 상품 사용 시작.

### 12.1 쿠팡 실제 성공 응답 형태 — 판정 수정 (#1054)

- 문서상 성공 응답은 `{ code:"200", data:{ code:"SUCCESS", ... } }`(중첩)인데, **가격 변경 API 의 실제 성공 응답은 최상위 `{ code:"SUCCESS", message:"가격 변경을 완료했습니다." }`** 였다.
- 파서가 중첩 형태만 인정해 첫 실사용 반영(4옵션 88,200→87,610)이 쿠팡에선 반영됐는데 `쿠팡 쓰기 실패: 가격 변경을 완료했습니다.` 로 보고됐고, 워크덱 판매가 동기화도 빠졌다.
- 수정:
  1. 최상위 `code === 'SUCCESS'` 를 성공으로 인정(중첩 data 가 ERROR 면 실패 유지).
  2. 응답이 실패로 해석돼도 **쓰기 전 가격 ≠ 목표가**였고 재조회(즉시 + 1.5초 후) 가격이 목표가면 성공으로 확정한다. 쓰기 전부터 목표가였으면 재조회로 뒤집지 않는다(거부된 최저가 변경을 성공으로 보고하지 않게).
  3. 실패 오류에 응답 원문(500자)을 남긴다.
- **최저가(`apMinSalePrice`)는 조회 API 가 없어** 재조회는 판매가만 증명한다. 결과 화면에 "최저가는 Wing 에서 확인" 안내.

| "확정" 외 선택지 없음                                      | 행마다 **[다른 상품 선택]**(판매채널 상품 검색 팝업, 기존 연결을 update 1회로 교체 — explicit) · **[매칭 안 함]** · [연결 해제]                              |
| 매칭하지 않을 옵션 처리 불가                               | **매칭 안 함**(`excludedAt`): 목록·자동 후보 경쟁·가격 반영 대상에서 제외, 수집 upsert 가 건드리지 않아 유지, 필터에서 해제. 상품명에 "판매중지"면 추천 배지 |
| 옵션마다 매칭 안 함 → 매번 저장·재조회                     | **다중 선택**(체크박스 + Shift 범위 + 하단 FloatingActionBar), 처리 후 조용한 재조회. 처리 대상은 화면에 보이는 선택만                                       |
| 진입점이 전체 채널 화면 상단에 있어 어색                   | 쿠팡 연동 채널 선택 시에만 채널 바 [상품 매칭], 화면 이름 "상품 매칭", `?channel=` 로 진입·복귀                                                              |

- **쿠팡 중복 리스팅**: 모호 110건 중 84건은 같은 판매채널 상품을 쿠팡 옵션 2개가 노리는 경우(쿠팡에 같은 상품을 리스팅 2개로 운영). **결정: 1:1 유지** — 가격을 쓸 쪽 하나만 확정하고 나머지는 매칭 안 함. 모호 행에 상대 옵션명을 표시한다.
- 기본 확정(후보·일괄)은 기존 연결·매칭 안 함 항목을 건드리지 않는다. 교체·되살리기는 사람이 직접 고른 경우(explicit)만.
- 쿠팡 상품 API 의 `statusName` 은 전부 "승인완료"라 판매중지 판단에 쓸 수 없다 → 상품명 휴리스틱.

### 12.3 반영 팝업 (#1052 #1056)

- 폭 확대(가로 스크롤 제거), **팝업 안에서 판매가·자동조정 최저가 수정**(기본값 = 시뮬 판매가·최소마진 가격, 시뮬 화면 값은 불변).
- **최저가 규칙 안내**: 쿠팡은 최저가 < 판매가여야 한다. 최저가 기본값이 최소마진 가격이라 판매가가 그보다 낮으면 막히고, **판매가를 낮추면 오히려 계속 막힌다**. [판매가를 ₩X로 올리기]/[최저가를 ₩Y로 내리기] 원클릭, 최저가가 최소마진 가격보다 낮으면 경고.
- **단계 분리**: 수정 → 반영 중 → 결과. 결과는 수정 화면에 섞지 않고, 결과 단계에서 [이전 단계로]/[닫기]. 진행 중이면 다시 열 때 반영 중 단계로.
- 안전장치: 미리보기를 계산한 (채널:판매가:최저가) 키가 지금 입력과 같을 때만 반영 가능, 늦게 온 이전 미리보기 응답 폐기, 빈 칸·0원 차단, 진행 중 잡(3분 초과 포함)·초기 잡 조회 전 반영 잠금, 3분 후에도 10초 간격 폴링 지속. **결과 단계의 재반영 버튼은 제거** — 화면에 없던 값(시뮬 기본값)·성공분까지 재전송될 수 있었다.

### 12.5 보류

- **네이버 스마트스토어 연동**: 커머스 API 가 부분 수정을 지원하지 않아(조회 → 전체 PUT, 누락 필드 삭제) 가격 쓰기가 다른 필드를 지울 위험이 크다. 일괄 수정은 상대값(±원/%)만, 가격 구조는 원상품 판매가 + 옵션 추가금. 진행 시 조회 전용 실측(Phase 0)부터.
- **채널 관리로 연동 설정 통합**: 쿠팡 자격증명은 계정 단위(채널 2개 + 광고 deck 공유)라 채널별 자격과 축이 맞지 않는다. 네이버 재개 시 "연동 계정" 단위로 함께 설계.
