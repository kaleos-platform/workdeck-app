### 개발 전용 계정의 Aside 브라우저 검증

사용자 요청으로 개발 환경에 QA 전용 계정을 직접 생성했다. 이메일 인증 완료 상태로 생성해 인증 메일은 보내지 않았다. 계정 로그인 → QA Space 생성 → 모집 관리 활성화 → `[QA] HTML 공고 검증` 초안 생성 → 제목 수정 → 공고 꾸미기 → 상세 HTML 화면 이동을 확인했다. 본문을 `QA 본문 저장 확인`으로 편집하고 저장 대기 후 완료 화면에 돌아왔을 때 HTML 코드와 격리된 미리보기에 해당 문구 및 inline style이 반영됐다.

추가 발견: 새 공고 생성 시 제목을 텍스트 블록에 복제하지만 이후 기본정보 제목 변경은 이 블록을 갱신하지 않아 HTML에 `제목 없는 공고`가 남는다. `app/api/hiring-posts/postings/route.ts`의 초기 블록 생성과 브라우저 화면에서 확인했다. 사용자가 꾸민 본문을 덮어쓰지 않도록 제목 입력 후 초안을 생성하거나 기본 제목 블록의 연결 상태를 명시하는 개선이 필요하다. 이번에는 본문을 직접 편집해 검증했다.

HTML 복사 버튼 클릭 후 `HTML 코드를 복사했습니다` 알림을 확인했다. clipboard 읽기는 권한이 사전 허용되지 않아 timeout이 발생했으므로 실제 clipboard 문자열 일치는 미검증이다. 새로고침 후 공고 제목과 iframe 본문 유지도 확인했다. 일반 저장 흐름의 결과이며 저장 중 즉시 이동·실패·역순 응답을 검증한 것은 아니다. 공개 발행·외부 메시지 발송·결제는 하지 않았다. 개발 서버에서 짧은 화면 전환 대기가 관찰됐지만 정밀 계측이나 production 성능 측정 결과는 아니다.

사용자가 로컬 개발 환경의 별도 테스트 공고 검증을 승인했다. `.env.local`의 인증 URL 및 DB 연결 식별 정보를 로컬에 저장된 운영 환경 파일과 비교해 다른 설정임을 확인했다. 비밀값은 출력하지 않았다.

구현:

- 제목 저장 요청 중 다시 수정·blur하면 마지막 값이 저장되지 않는 문제를 지연 응답 테스트로 재현하고, 순차 저장으로 수정했다.
- 외부 HTML에 제목·문단·목록·인용·링크·이미지의 기본 inline style을 추가했다. 기존 앱 본문의 기본 렌더링 경로는 유지했다.
- 상세 화면 첫 영역에 `HTML 복사`를 배치하고 원문 코드는 접었다 펼치도록 변경했다.
- 외부 게시용 미리보기를 sandbox iframe으로 격리했다. 이는 대상 채용 사이트가 HTML을 변환한 결과까지 보장하지 않으므로 해당 사이트의 미리보기 확인 안내를 추가했다.
- 초안에서도 HTML을 사용할 수 있고 내부 지원 링크는 발행 이후에 공개된다는 차이를 안내했다.

검증: 관련 Jest 4개 suite/5개 테스트 통과(수정 전 실패 확인), `npm run typecheck` 통과, `npm run lint` 0 errors/70 warnings, 변경 파일 ESLint 경고 없음. `npm run build`는 기존 잠금 및 샌드박스 내 정체로 재시도 후 실행 제한 밖에서 성공했다(325개 정적 페이지 생성, exit 0). 로그인된 로컬 화면의 생성·저장·복사 알림 및 새로고침 검증은 위 기록을 따른다. 실제 clipboard 문자열과 사람인/알바몬 붙여넣기는 미검증이다. 운영 배포는 하지 않았다.

Aside 일반 창에서 localhost 로그인 화면까지 확인했다. 사용자 개발 계정 로그인이 필요해 실제 테스트 공고는 아직 생성하지 않았다. 본문 debounce 저장 완료 대기·필터/페이지 이동 등 나머지 계획은 미완료이며, 이번 제목 저장 수정이 편집기 전체 저장 순서를 보장한다는 의미는 아니다.

## 확인 사항

### 1. 핵심 결과물인 HTML 복사의 우선순위가 낮음 — P1

`app/d/recruiting/home/page.tsx`와 `postings/page.tsx`는 공개 지원 페이지 운영을 중심으로 설명한다. 홈은 최근 작업 없이 정적인 시작 안내를 제공한다. 홈의 새 공고 버튼은 생성이 아니라 공고 목록으로 이동한다.

`src/components/hiring-posts/posting-detail.tsx`는 지원서 링크 → 공고 링크 → HTML 순서다. `build-wizard.tsx`의 마지막 CTA는 공고 등록·완료이며 HTML 복사는 없다. 사용자는 편집을 끝내고 상세로 이동해야 복사할 수 있다.

### 2. 지원서 설정이 기본 편집 흐름의 중간에 있음 — P1

`wizard-stepper.tsx`: 기본 정보 → 지원서 폼 제작 → 공고 꾸미기. 지원서 단계에는 건너뛰기가 있고 상단 단계 직접 이동도 가능하므로 필수 입력 장벽은 아니다. 다만 주 고객에게 부차적인 작업이 주된 순서에 놓인다.

HTML 복사 자체는 상세 화면에서 DRAFT에도 제공된다. 이를 발행 필수 기능으로 잘못 해석하거나 새 제한을 추가하면 안 된다. 공개 지원 접수 활성화와 외부 HTML 사용은 분명하게 구분한다.

### 3. 외부 HTML과 내부 미리보기의 CSS 환경이 다름 — P0 검증

`render-embed-html.ts`는 이미지·버튼·직무 등에 inline style을 출력하지만 텍스트 블록은 `renderTiptapHtml`의 결과를 감싼다. `render-tiptap.ts`의 heading·paragraph·list 출력 전체에 `prose.ts`의 타이포 스타일이 inline으로 주입되는 구조는 아니다.

상세 미리보기는 `HIRING_PROSE_CLASS`를 추가 적용한다. 그러므로 코드가 같아도 외부 사이트에서 동일하게 보인다는 설명은 현재 검증 근거가 없다. 스타일 격리된 미리보기와 독립 HTML 스타일이 필요하다. 특정 사이트에서 실제 깨졌다는 재현 결과는 아직 없다.

`renderTiptapHtml`은 변환 실패 시 빈 문자열을 반환한다. HTML renderer는 이미지 경로가 없는 이미지/디자인 블록도 생략한다. 편집 결과가 조용히 누락되는 것을 복사 전 검출해야 한다.

### 4. 저장 완료와 복사·화면 이동의 동기화 검증 필요 — P0

`content-block-editor.tsx`는 텍스트를 700ms debounce로 저장한다. 오버레이 닫기 시 flush는 있으나 비동기 완료를 기다리지 않는다. 템플릿 저장은 postingId를 보내 서버 데이터를 이용하며, 공통 저장 완료 대기를 거치지 않는다. `build-wizard.tsx`의 완료 Link도 pending 저장 완료를 기다리지 않는다.

느린 네트워크에서 마지막 편집 직후 완료·템플릿 저장을 누르면 최신 데이터가 반영되지 않을 가능성이 있다. 실제 데이터 유실을 확인한 것은 아니므로 지연 응답으로 재현한 후 수정한다. 제목 blur 저장에도 연속 수정 중 저장 요청 생략 경로가 있어 함께 확인한다.

### 5. 누적 공고 탐색과 로딩 근거 보완 — P1/P2

`listPostings`는 최신 작성순 최대 500건을 가져오며 `postings-table.tsx`는 클라이언트 상태 탭으로 필터링한다. 검색·서버 페이지 이동이 없어 500건을 넘으면 이전 공고를 이 화면에서 찾을 수 없다. 현재 고객이 한 Space에서 500건을 초과했다는 집계는 아직 없다.

편집 route는 첫 기본정보 화면에서도 모든 콘텐츠 data를 전달한다. 큰 디자인 JSON의 초기 전송량을 측정해야 한다. 모집 관리 하위의 전용 loading.tsx/error.tsx도 발견되지 않았다. 실제 느림의 원인은 측정 전 확정하지 않는다.

### 6. AI 작업 지침의 기준 파일 누락 — P1

`.codex/skills/workdeck-ui/SKILL.md`가 최우선 디자인 기준으로 지정하는 루트 `DESIGN.md`가 없고, 파일명 검색에서도 대체 기준 문서를 찾지 못했다. 기존 화면 패턴과 `docs/rules/02-architecture.md`를 현재 평가 기준으로 사용했다. Claude/Codex가 같은 UI를 만들려면 기준 파일의 실제 위치를 확정하고 동일 문서를 참조해야 한다.
