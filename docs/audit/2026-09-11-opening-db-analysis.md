## 해석과 deck 경계 초안

1. 모집 관리 단일 deck 유지가 현재의 기본안이다. 공고 제작·공개 페이지·지원 접수·지원자 관리·매장/직무 설정은 같은 업무 흐름으로 묶는다.
2. 공고 제작과 템플릿 사용이 지원 접수보다 넓게 관찰된다. 외부 채용 사이트용 콘텐츠 제작이 핵심 가치일 가능성이 있지만, 이미지 다운로드·외부 게시를 이 집계로 입증하지는 못했다. 고객 사용 목적 확인이 필요하다.
3. 외부 배포/부스팅은 코드에 존재하지만 해당 DB의 저장 데이터는 0건이다. 우선 이전 필수 기능에서 제외하는 가설을 세우되, 외부 시스템이나 삭제된 이력까지 미사용으로 단정하지 않는다.
4. 채용 콘텐츠 제작을 별도 deck으로 분리하는 대안은 독립 구매 의사와 운영 흐름이 확인될 때 검토한다. 지금 분리하면 공고·템플릿·매장 데이터를 공유하는 경계와 중복 과금 문제가 추가된다.
5. 공통 Space·회원·권한·결제는 Workdeck 기반 기능에 통합한다. 매장·직무를 독립 deck으로 분리할 데이터 근거는 아직 없다.

## Workdeck과의 1차 대조

Prisma의 HiringPosting, HiringContent, HiringDetailTemplate, HiringApplication이 이미 공고·콘텐츠·템플릿·익명 지원서를 표현한다. 상세 폼 스키마와 제출 데이터는 별도 Json 필드이며, 지원자 개인정보는 암호화 필드와 hash로 분리되어 있다. 템플릿에는 이관 출처용 sourceRef가 있다.

따라서 신규 deck 생성보다 기존 recruiting의 기능 충실도와 이전 도구 검증이 우선이다. 이것은 스키마 수준의 대조이며 UI·API가 모두 이관 요구를 충족한다는 결론은 아니다.

## 다음 검증 순서

1. 기존 유료 고객이 공고 제작과 지원자 관리 중 무엇을 구매하는지 확인.
2. 대표 고객 선정: 콘텐츠 중심, 지원 접수 중심, 다매장 고객. 익명 집계와 운영 담당자의 고객 확인을 결합.
3. 기존 ID → Workdeck ID 대응, Space·멤버 권한, 공고 uuid와 공개 URL, 동적 폼, 암호화/검색 hash 전환 정의.
4. 파일 50,427건을 전부 복사 대상으로 간주하지 않고 연결 관계·소프트 삭제·참조 유무·S3 실제 객체·크기 확인.
5. 결제 원장과 현재 구독 대조, 이전 시 중복 청구 방지와 기존 구독 종료 절차 정의.
6. dry-run 이관 및 건수·관계·파일 접근·공개 지원·관리자 권한 검증 후 대표 고객부터 전환.
7. Workdeck 전체 UI/UX·성능·개발 지침·AI/worker 분석을 결합한 실행 로드맵 작성.
