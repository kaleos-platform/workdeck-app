# UX가 바뀌는 UI 작업은 구현 전에 미리보기로 합의 (2026-11-16)

## 목표

에디 지시: UI 작업에서 디자인을 미리 보고 싶다. 기존 Excalidraw 시각 계획(`ui-plan`)을 활용도·토큰 관점에서 검토하고, 단순 작업(요소 이동 등)을 뺀 **UX가 바뀌는 주요 작업**에서는 반드시 쓰게 규칙을 정한다.

## 검토 (현재 `ui-plan` 사용 실태, develop `docs/design/plans/`)

| 작업                  | 시점            | 파일                                        | 크기    |
| --------------------- | --------------- | ------------------------------------------- | ------- |
| integrations-settings | 2026-11-01 시범 | 와이어프레임 6 + plan.md (현재안 1 + B안 5) | 약 28KB |
| recruiting-landing    | 2026-11-13      | 와이어프레임 1 + plan.md                    | 약 23KB |
| admin-deck-management | 2026-11-14      | 흐름도 1 + 와이어프레임 1 + plan.md         | 약 6KB  |

- **활용도:** 2주 동안 3건(시범 제외 실제 2건)에 쓰였다. 승인은 매번 대화로 했고(admin: "세 차례 질문으로 사용자가 승인한 구조를 기록"), **에디가 캔버스에서 그림을 고친 적은 0건**이다(12개 파일 모두 커밋 1회, 에이전트가 쓴 skeleton 형식 그대로). integrations는 구현 중 바뀐 결정을 그림이 아니라 plan.md 메모에 적었다("그림보다 이 메모가 최신").
  - 쓸모 있었던 것: 구조·흐름을 글보다 빨리 보여 주는 것, 안 비교(B안 5장), 결정 기록.
  - 쓰이지 않은 것: "에디가 직접 끌어 고치고 저장 → git diff로 읽기" 루프.
- **토큰:** 와이어프레임 작성은 화면당 약 1~22KB(대략 0.4k~7k 토큰), 작업당 6k~28KB다. 자가 확인 캡처 1~2장을 더해도 구현 세션 전체에 비하면 작다. 큰 비용은 요소가 많은 한 장(랜딩 22KB)과 안을 여러 개 그릴 때 생긴다.
- **불편:** `/dev/plan/<task>` 화면을 보려면 dev 서버와 tailnet 작업대가 떠 있어야 한다. 에디가 비동기로 보기 어렵다.

## 결정

1. **대상(반드시 `ui-plan`)** — UX가 바뀌는 작업:
   - 새 화면·새 route, 화면 흐름·단계·진입점·메뉴 구조 변경
   - 정보 구조 변경(무엇을 어느 화면·탭·섹션에 둘지)
   - 상호작용 방식 변경(폼↔마법사, 표↔카드, 모달↔페이지, 일괄 작업 방식)
   - 모바일 배치를 새로 짜는 작업, 여러 화면에 걸친 같은 패턴 변경
2. **제외(라이브 작업대에서 바로)** — 같은 영역 안 요소 이동·순서, 간격·색·글꼴·문구, 기존 패턴에 열·필드·버튼 하나 추가, 레이아웃 버그 수정. 애매하면 에디에게 "미리보기 할까요?" 한 줄로 묻는다.
3. **합의 방식 바꿈:** 캔버스 편집은 선택. 기본은 **미리보기 캡처(PNG) + 짧은 질문**으로 승인받는다. 에이전트가 ego로 `/dev/plan/<task>`를 캡처해 경로를 알리고, 라이브 주소는 함께 준다.
4. **토큰 상한:** 화면당 요소 40개 안쪽, 안은 최대 2개(현재안 포함 3장), 바뀌는 곳만 번호. 에디가 캔버스를 고친 경우에만 `git diff`를 읽는다(전체 파일 재독 금지).
5. **결정 기록:** 승인 뒤 바뀐 결정은 plan.md에 적고, 구조가 확정되면 `DESIGN.md` §8 결정 기록에 한 줄(고른 안/버린 안: 이유).
