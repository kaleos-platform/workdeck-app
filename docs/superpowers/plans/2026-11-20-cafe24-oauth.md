## 1. 목표

워크덱 Space 가 카페24 쇼핑몰(ameaning24)의 Admin API 를 **주문 읽기+쓰기 권한**으로 호출할 수 있게 연결한다. 이번 범위는 **연결·토큰 관리·조회 1건 확인까지**다. 주문 수집·배송 처리·송장 등록은 주문 파이프라인 계획에서 한다.

완료 기준: 운영에서 설정 > 연동 > 카페24 팝업에 앱 정보 저장 → 「카페24에서 승인」 → 쇼핑몰 관리자 승인 → 워크덱 복귀 「연결됨」 → 서버가 주문 목록 조회(읽기) 1회 성공. 이후 토큰이 사람 개입 없이 유지된다(2시간 액세스 / 2주 갱신 토큰).

## 4. 변경 파일

1. 신규 `src/lib/cafe24/oauth-state.ts` — state = base64url(JSON{spaceId,userId,clientId,mallId,nonceHash,exp}) + HMAC. 키는 `HMAC(SLACK_SIGNING_SECRET, 'cafe24-oauth-state:v1')` 로 도메인 분리(새 env 없음, 없으면 install 503). Slack state 와 키가 달라 서로 못 씀. **일회용 nonce**: install 이 랜덤 nonce 를 httpOnly·Secure·SameSite=Lax·Path=`/api/integrations/cafe24` 쿠키(10분)에 넣고 state 엔 해시만 → callback 이 쿠키와 대조 후 즉시 삭제(재사용·다른 브라우저 세션 차단).
2. `app/api/spaces/[spaceId]/credentials/[provider]/route.ts` — `cafe24` 스키마:
   - secret `{ clientId, clientSecret }`(저장 시 토큰 필드는 받지 않음)
   - config `{ mallId: /^[a-z0-9][a-z0-9-]{1,49}$/ }`
   - clientId·mallId 가 바뀌면 기존 토큰 폐기(연결 상태 → 승인 필요). 같은 값으로 시크릿만 바꾸면 토큰 유지.
   - 기존 `saveSpaceCredential`(무조건 upsert) 대신 카페24 전용 저장 함수: 읽기 → 병합 → 조건부 쓰기(아래 '쓰기 규칙'). 충돌이면 409.
3. 신규 `src/lib/cafe24/client.ts`
   - `authorizeUrl(mallId, clientId, state, redirectUri)` — `https://{mallId}.cafe24api.com/api/v2/oauth/authorize`, scope `mall.read_order mall.write_order`(**공백 구분**, 문서 확인). 이름은 문서끼리 표기가 달라(`mall.read_order` / `read_order` / `READ_ORDER`) 운영 승인 응답의 `scopes` 로 확정
   - `exchangeCode` / `refreshTokens` — `POST https://{mallId}.cafe24api.com/api/v2/oauth/token`, `Authorization: Basic base64(clientId:clientSecret)`, form body
   - `getAccessToken(spaceId)` — 만료 5분 전이면 갱신. **DB 트랜잭션·락을 외부 HTTP 동안 잡지 않는다**(서버리스·운영 pool 연결 수가 작아 막힘 위험). 대신 낙관적 버전 확인:
     1. 행 읽기(`config.credVersion` = 버전, 갱신 토큰 R0) → 2) 갱신 HTTP(타임아웃 8초) → 3) 조건부 쓰기로 새 토큰 저장(버전+1).
     - **갱신 lease**: 갱신 HTTP 전에 조건부 쓰기로 `config.refreshLease = { owner: 랜덤id, until: 지금+20초 }`(버전+1)를 잡는다. 이미 유효한 lease 가 있으면 HTTP 를 보내지 않고 0.5초 간격으로 최대 20초 다시 읽으며 새 토큰을 기다린다(lease 시간 20초 > HTTP 타임아웃 8초 + 저장 여유). 저장 시 lease 해제.
     - lease 를 잡고도 `invalid_grant` 를 받으면(lease 밖에서 회전된 경우) 다시 읽어 갱신 토큰이 바뀌었으면 그 값 사용, 그대로면 그때만 `reauth_required`. **유효한 다른 lease 가 있는 동안의 invalid_grant 는 실패로 확정하지 않는다.**
     - lease 만료(소유 실행이 죽음) 후에는 다른 실행이 lease 를 다시 잡는다.
     - 3. 이 0행이면 다시 읽어 판단: (a) 저장된 clientId·mallId 가 내가 읽은 값과 다름(재설정) → 내 토큰 버림, 그 상태를 따름 (b) 저장된 갱신 토큰이 R0 가 아님(다른 실행이 회전) → 그 값을 사용 (c) 갱신 토큰이 여전히 R0(토큰과 무관한 변경) → **내 새 토큰을 최신 버전에 다시 조건부 병합**(최대 3회). 3회 모두 실패하면 `reauth_required` + 알림.
     - **알려진 한계**: 카페24가 옛 갱신 토큰을 폐기한 뒤 응답 유실·함수 종료·DB 저장 실패가 나면 저장된 토큰은 이미 죽은 상태 → 복구 불가 → `config.status='reauth_required'` + 알림 → 연결 팝업의 「다시 승인」 1회로 복구. 매일 1회 + 사용 시점 갱신뿐이라 빈도는 낮다.
   - `cafe24Get(spaceId, path, query)` — `X-Cafe24-Api-Version: 2026-09-01` 고정(선택 헤더지만 앱 설정 변경에 끌려가지 않게), 순간 유량 버킷 40·초당 2 감소·10분 3,000회 → 직렬 호출 + `X-Api-Call-Limit`(`사용/용량`) 30 이상이면 1초 대기, 429 는 지수 대기 3회, 401 이면 1회 갱신 후 재시도
   - **오류 기록 규칙**: 토큰·주문 응답 본문, 요청 헤더(Basic·Bearer)는 오류 메시지·로그·DB·Slack 어디에도 넣지 않는다. 기록은 `HTTP 상태 + 응답 JSON 의 error 코드(허용 목록: invalid_grant, invalid_client, invalid_request, unauthorized_client, insufficient_scope, rate_limited 등) + 우리 쪽 단계명` 만. `maskSecrets` 에 의존하지 않는다.
   - 오류 메시지에 토큰·시크릿 금지(`maskSecrets`)
4. 신규 `app/api/integrations/cafe24/install/route.ts` — **POST 전용**(연결 카드의 폼 제출). `Origin` 이 앱 도메인과 같아야 함(교차 사이트 시작 차단). 로그인 + Space ADMIN + MFA aal2. 자격증명 없으면 400. nonce 쿠키 설정 + 서명 state(10분) 로 authorize 에 303 리다이렉트.
5. 신규 `app/api/integrations/cafe24/callback/route.ts`
   - state 서명·만료 검증 + nonce 쿠키 일치(후 즉시 삭제) + **현재 로그인 사용자 = state.userId** + 여전히 ADMIN + aal2 확인
   - 저장된 clientId·mallId 가 state 의 값과 같은지 확인(승인 도중 설정이 바뀌었으면 토큰 저장 안 함)
   - `error` 파라미터(사용자 거부) → `?open=cafe24&cafe24=denied`
   - code 교환(redirect_uri 는 install 과 바이트 동일 `buildAppUrl('/api/integrations/cafe24/callback')`)
   - 응답 `mall_id` = 저장된 mallId, `scopes` 를 정규화(`mall.` 접두사 제거·소문자)해 `read_order`·`write_order` 포함 확인 — 다르면 저장 안 하고 오류
   - 토큰 저장은 쓰기 규칙(조건부 쓰기)으로. 저장 후 **주문 목록 조회 1회**(최근 1일, limit 1)로 실제 동작 확인 → `config.status='connected'`, `connectedAt`, `connectedBy`, `scopes`

6. `src/lib/agent/integrations/credential-health.ts` — `PROBES.cafe24`: `getAccessToken`(필요 시 갱신) + 주문 목록 조회 1건. 매일 실행이라 갱신 토큰(2주)이 끊기지 않는다. 실패 시 기존 healthError·Slack 알림 경로 그대로. `invalid_grant`(갱신 토큰 죽음)면 `reauth_required`.

### 쓰기 규칙(등록·콜백·갱신 공통)

- 버전 = `config.credVersion`(정수). `updatedAt` 은 시간값이라 같은 밀리초 충돌·시계 차이로 버전 역할을 못 해 쓰지 않는다. 마이그레이션 없이 config JSON 에 둔다.
- 세 경로(등록·콜백·갱신)만 버전을 올린다. 기존 health·오류 기록(`healthError`·`healthAlertedAt`·`lastError` 컬럼만 update)은 버전을 건드리지 않으므로 토큰 쓰기와 충돌하지 않는다.
- 조건부 쓰기 = `updateMany where { id, provider:'cafe24', config: { path: ['credVersion'], equals: 읽은 버전 } }` 로 `encryptedPayload·iv·config(버전+1)` 갱신. Prisma JSON path 필터가 Postgres 에서 기대대로 동작하는지 dev DB 통합 테스트로 확인(안 되면 `$executeRaw` 의 `config->>'credVersion' = $n` 조건).
- **최초 등록**: 행이 없으면 `create`(`credVersion: 1`). `@@unique([spaceId, provider])` 충돌(동시 생성)이면 다시 읽고 409.
- 0행 처리: 등록 = 409(다시 시도 안내), 콜백 = 다시 읽어 clientId·mallId 가 state 와 같고 버전만 바뀌었으면 1회 재시도, 아니면 오류 리다이렉트, 갱신 = 위 (a)(b)(c).
- 무조건 upsert(`saveSpaceCredential`) 는 카페24 에 쓰지 않는다.

8. 테스트(jest): state purpose 분리, install 권한(MEMBER 403·aal1 차단), callback(state 위조·다른 사용자·mall 불일치·scope 부족·거부), 토큰 갱신(만료 임박만 갱신, 락 안 재확인으로 이중 갱신 없음 — 모의 fetch 호출 수 검증), 401 재시도 1회, 스키마(clientId 변경 시 토큰 폐기), **동시성**(갱신 두 개 동시 → HTTP 성공 1회·나머지는 저장값 사용, 성공 응답·DB 저장을 1.5초 이상 늦춰도 대기 쪽이 재승인으로 떨어지지 않음, 갱신 중 clientId 변경 → 옛 토큰 재저장 안 됨, 콜백 중 설정 변경 → 저장 안 함), **nonce**(쿠키 없음·불일치·재사용 거부), **install POST 의 Origin 불일치 거부**, **비밀값 미노출**(Basic·토큰·응답 본문을 넣은 실패를 주입해 오류 메시지·`lastError`·`healthError`·console 출력에 없음 확인).

## 7. 롤백

- 코드 되돌림(revert): 타일·라우트·probe 가 함께 사라진다. probe 가 없어지면 토큰 갱신이 멈춰 2주 뒤 자연 만료 — 이 기능만 쓰는 토큰이라 다른 기능 영향 없음. 저장된 `SpaceCredential(provider=cafe24)` 행은 남지만 읽는 코드가 없다.
- 완전 해제: ① 카페24 쇼핑몰 관리자에서 앱 삭제(토큰 즉시 무효) ② 워크덱 행 삭제는 DELETE 라우트가 없으므로(기존 정책) 사용자 승인 후 운영 데이터 1행 삭제.
- 재연결: 코드 재배포 후 팝업 「다시 승인」.
- Slack state 코드는 건드리지 않아 Slack 설치 흐름 영향 없음.

## 8. 위험

- 갱신 토큰 회전 경쟁·늦은 쓰기 → 정수 버전 조건부 쓰기 + 0행 시 원인별 처리(쓰기 규칙). 회전 직후 응답 유실은 복구 불가 → 재승인(알려진 한계).
- 매일 health 가 실패하면 2주 뒤 연결 끊김 → 기존 healthError 첫 실패 Slack 알림으로 충분(연속 횟수 추적은 안 함). `invalid_grant` 는 즉시 「재승인 필요」.
- 카페24 API 버전 헤더·호출 제한 값은 문서 확인 결과로 확정(아래 11).
- 앱이 「제작중」 상태로 자사몰 설치가 되는지 — 카페24는 제작중 앱을 개발자 본인 쇼핑몰에 테스트 설치 가능(「테스트 실행」). 운영 검증 첫 단계에서 확인, 안 되면 사용자와 다음 조치 결정.

## 11. 카페24 문서 확인 결과

apidocs.cafe24.com(2026-09-01 버전) 기준, 서브에이전트 조회(2026-11-20).

- authorize `https://{mall_id}.cafe24api.com/api/v2/oauth/authorize?response_type=code&client_id&state&redirect_uri&scope` — 브라우저에서만, 코드 1분·1회용, scope 공백 구분.
- token `POST https://{mall_id}.cafe24api.com/api/v2/oauth/token`, `Authorization: Basic base64(client_id:client_secret)`, form `grant_type=authorization_code&code&redirect_uri`. 응답 `access_token, expires_at, refresh_token, refresh_token_expires_at, client_id, mall_id, user_id, scopes, issued_at, shop_no, token_type`.
- 갱신 `grant_type=refresh_token&refresh_token=…` → **새 refresh_token 발급, 이전 것은 자동 폐기**(회전 확정 → 4-3 락 필수). 액세스 2시간, 갱신 2주.
- 버전 헤더 `X-Cafe24-Api-Version` 선택(미지정 시 앱 설정 버전), 형식 yyyy-mm-dd.
- 호출 제한: 버킷 40·초당 2 감소, 10분 3,000회·호출시간 600초, `X-Api-Call-Limit: n/40`, 초과 429. 주문 목록 `GET /api/v2/admin/orders` 요청당 최대 100건.
- 확인 못 함: scope 정식 표기(앞 참조), 주문 목록 기간 파라미터 상한, 배송(shipments) API 필드 — 배송은 이번 범위 밖.
