## 설계 결정

### 태그 로딩 범위

- `@next/third-parties` 의 `GoogleAnalytics` 는 `gtag('config', id)` 를 고정 출력해 `send_page_view` 를 끌 수 없다
  → 의존성 추가 없이 `next/script` 로 gtag 스니펫을 직접 넣는 컴포넌트 1개(`src/components/analytics/google-tag.tsx`).
- `config` 는 항상 `send_page_view: false`. 페이지 조회는 우리가 보낸다(아래).
- 로딩 위치: `app/(marketing)/layout.tsx`, `app/(auth)/layout.tsx`(signup·login·workspace-setup), `/my-deck`(구독·체험 지점),
  `/settings/billing`(구독 시작 2번째 경로). 대시보드(`/d/*`)·어드민·설정 기타 화면은 로딩하지 않는다.
- `NEXT_PUBLIC_GA_ID` 가 없으면 아무것도 렌더하지 않는다 → Vercel **Production 환경에만** 설정, preview·로컬은 미측정.

### 페이지 조회·자동 수집 (Codex 지적 1 반영)

- GA4 향상된 측정은 **전부 끈다**(에디 GA4 콘솔). 스크롤·이탈 클릭·파일 다운로드도 끈다 → 대시보드로 SPA 이동한 뒤에도 자동 이벤트가 나가지 않는다.
- `page_view` 는 위 로딩 위치에서만 `usePathname` 변화마다 우리가 보낸다.
- 모든 이벤트(page_view 포함)의 `page_location` 은 `track()` 이 직접 만든다: 오리진 + pathname + **허용 utm 5종만**.
  utm 값은 100자로 자르고 `@` 가 들어 있으면 버린다(이메일 유입 방지). 다른 쿼리(`spaceId`, `subscribe=`, `redirectTo` 등)는 버린다.
- `page_referrer` 도 같은 규칙으로 정규화해 보낸다(오리진+pathname만). 외부 사이트 referrer 는 오리진만 남긴다.
- `/d/*`·`/admin`·`/settings`(결제 제외) 경로에서는 `track()` 자체가 아무것도 보내지 않는다(경로 가드) — SPA 로 넘어가도 안전.

### 이벤트 (모두 클라이언트, `src/lib/analytics.ts` 의 `track(name, params)` 한 함수 경유 — gtag 없으면 no-op)

| 이벤트          | 발생 지점                                                                                                          | 파라미터                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| `cta_click`     | 마케팅 레이아웃 클릭 위임 리스너 1개: app 오리진 `/signup`·`/login` 으로 가는 `<a>`                                | `cta`(signup/login), `deck`           |
| `generate_lead` | `lead-form.tsx` 제출 `res.ok`                                                                                      | `deck`                                |
| `sign_up`       | `workspace-setup-form.tsx` 응답 **201** 일 때만 (200=기존 작업 공간 재요청은 제외)                                 | 없음                                  |
| `trial_start`   | `my-deck-client.tsx` `confirmAddDeck` 응답 `trialStarted === true`                                                 | `deck`                                |
| `subscribe`     | 구독 API 성공 **직후**(후속 업무 활성화 결과와 무관): my-deck `confirmSubscribe`, 설정 화면 구독 시작·`runAddDeck` | `deck`, `kind`(start/add), `reserved` |

- **`sign_up` 정의 = 가입 완료(작업 공간 생성).** 이메일 인증 후 작업 공간을 만들지 않고 이탈한 사람은 빠진다. 초대 합류자는 고객 전환이 아니므로 제외가 맞다.
- **`purchase` 는 이번 범위에서 뺀다 (Codex 지적 2 반영).** 구독 API 성공은 즉시 결제·일할 결제·0원 해지 취소·체험 예약을 모두 포함하고
  보장가도 적용돼 클라이언트가 실제 청구액을 알 수 없다. 월 가격을 매출로 보내면 GA4 매출이 왜곡된다.
  → 매출 없는 `subscribe` 로 구독 확정만 센다. 실제 청구 매출(`purchase`)은 후속 작업: 구독 시 `_ga` client_id 저장 → 청구 성공 시
  서버가 결제액·결제 ID(transaction_id)로 Measurement Protocol 전송.
- **`trialStarted` 판정 (Codex 지적 4 반영):** 미리 읽은 상태가 아니라 `createMany(skipDuplicates)`·조건부 `updateMany` 의 실제 `count` 합 > 0 으로 판정한다
  → 동시 요청 중 정확히 하나만 true. 동시 요청 테스트 추가.
  ponytail: 트랜잭션 커밋 뒤 finance 시드가 실패하면 500 이 돌아가 `trial_start` 가 빠진다(재시도는 409). 드문 경로라 누락을 감수하고,
  주간 리포트에서 DB `SpaceDeckAccess.trialEndsAt` 건수와 대조해 차이를 본다.
- 클라이언트 이벤트는 광고 차단기·응답 유실로 일부 빠진다. 정답 수치는 DB(가입=`User.signupSource`, 체험·구독=billing 테이블)이고 GA4 는 유입 경로별 비율을 보는 용도.
