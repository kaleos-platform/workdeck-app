# 의견 남기기 비용·수명주기 검토

작성: 2026-11-27 · 대상 설계 `2026-11-27-user-feedback-design.md`

## 결론

기존 500MB 상한·이미지 축소·자동 삭제는 사용량을 줄이지만 **Supabase 추가 과금 없음의 보장은 아니다**. 운영 조직의 플랜·Spend Cap·Storage/egress/DB 디스크 여유가 확인되기 전에는 비용 조건이 충족됐다고 판단하거나 기능을 운영 활성화하지 않는다. 기능 구현은 로컬에서 준비할 수 있다.

원래 설계의 기능 범위와 사용자 결정은 유지한다. 아래 미확인 항목을 실제 설정으로 확인하고 적용할 운영 조건을 확정해야 한다. 자격증명·환경 파일·운영 DB를 조회해 우회 확인하지 않는다.

## 공식 문서 확인

- [Control your costs](https://supabase.com/docs/guides/platform/cost-control): Pro의 Spend Cap은 Storage Size·egress·Disk Size 등을 포함하지만 Compute·Branching Compute·일부 부가 항목은 제외한다. 한도 초과 시 서비스 제한이 생길 수 있다. 조직 단위 설정이므로 이 기능만의 예산이 아니다.
- [Storage size usage](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size): Pro 포함량은 100GB, 초과 단가는 $0.0213/GB·월이며 실제 계산은 GB-hours 기준이다. 현재 객체 크기 합계와 청구 기간 사용량은 같지 않다.
- [Egress usage](https://supabase.com/docs/guides/platform/manage-your-usage/egress): 파일 다운로드뿐 아니라 DB 등에서 나가는 데이터도 egress에 포함된다. 작은 저장 용량이어도 반복 다운로드 트래픽을 제한하지는 못한다.

현재 Workdeck 조직의 플랜·사용량·Spend Cap 상태는 미확인이다. 전임자의 Pro 추정은 실제 확인 사실로 취급하지 않는다.

## 기존 설계에서 보완할 점

1. **상한 검사는 예약량을 포함해 원자적으로 수행한다.** `현재 합계 >= 상한`만 검사하면 이번 요청 3MB 및 동시 요청만큼 초과한다. `현재 점유 + 진행 중 예약 + 이번 요청 바이트 <= 상한`으로 판정한다. DB 트랜잭션에서 공통 advisory transaction lock을 잡고 미삭제/미업로드 첨부 행까지 합산·예약한다. 네트워크 업로드 동안 DB lock을 유지하지 않는다. 예약 행은 객체 경로 생성과 함께 저장하고 실패·타임아웃 후 정리 대상으로 남긴다. 업로드/삭제 경쟁은 예약의 상태 전이로 차단한다.
2. **삭제 성공 전에는 용량을 해제하지 않는다.** Storage 삭제 실패가 난 객체와 업로드 성공 여부가 불확실한 객체도 상한에 포함한다. 성공한 삭제만 반영하고 재실행은 멱등적으로 동작해야 한다. 데이터 행만 삭제하는 rollback은 파일 경로를 잃을 수 있다.
3. **탈퇴 후 삭제 재시도 정보를 보존한다.** 실제 비테스트 사용자 삭제 경로 검색 결과 `app/api/admin/users/[id]/route.ts`의 `tx.user.delete` 1곳을 확인했다. Cascade 전에 같은 transaction에서 삭제 작업을 별도 큐에 적재한다. 큐는 User/Feedback FK 없이 무작위 객체 경로만 보존하며 본문·이메일을 복제하지 않는다. DB commit 후 즉시 삭제를 시도하고 실패는 cron이 재시도한다. 이 큐가 있는 동안에도 해당 파일 바이트를 점유량으로 센다. 다른 경로 도입 시 재검색한다.
4. **정리와 상태 재개 경쟁을 검증한다.** cron이 후보를 찾은 뒤 상태가 NEW로 바뀌면 잘못 삭제할 수 있다. 첨부 삭제 작업을 DB에서 claim하고 상태 변경도 동일 피드백 행을 잠가 직렬화한다. 이미 삭제 claim된 동안 재개 요청에는 409와 재시도 안내를 반환한다. 삭제 완료 후 재개 시 본문은 복구되지만 이미지가 삭제됐다는 이력을 표시한다.
5. **비용 상한 도달 시 묵시적 첨부 유실 금지.** 본문만 저장했으면 응답에 `attachmentsAccepted: false` 및 사유를 명시하고 Dialog에 ‘의견은 접수됐지만 이미지는 저장되지 않았어요’를 표시한다. 성공 토스트만 띄우지 않는다. 잘못된 MIME·크기 등 입력 오류는 저장 전 400으로 거절한다.
6. **Vercel cron도 Supabase 부하가 있다.** 실행 위치가 Vercel이어도 DB 조회·Storage 삭제 요청은 Supabase를 사용한다. 하루 한 번, 인덱스 조건, 제한된 batch와 실행 시간으로 제어하며 ‘컴퓨트 부담 없음’이라고 설명하지 않는다.
7. **서명 URL은 egress 상한이 아니다.** 만료 시간은 접근 기간만 제한한다. 목록 이미지 미로드, 상세에서만 URL 발급, 이미지 변환 미사용을 유지한다. 비용 보장의 최종 조건은 실제 조직 과금 설정이다.
8. **화면 주소의 query를 그대로 남기지 않는다.** 원래 설계는 pathname+search 저장이지만 민감한 검색어나 토큰이 포함될 수 있다. 기본 pathname만 저장하고 재현에 꼭 필요한 query만 명시적 allowlist로 저장하는 변경안을 제안한다. 전체 query를 Slack·로그·DB로 보내지 않는다.
9. **rate limit의 의존성을 작게 유지한다.** 기존 `checkRateLimit`는 Prisma/PII까지 가져오는 `hiring/applications.ts`에 있다. feedback이 hiring 도메인 전체를 import하지 않도록 기존 구현을 작은 공용 모듈로 옮기고 기존 export를 유지한다. 인스턴스별 rate limit은 비용 상한의 근거로 쓰지 않는다.

## 비용 조건 선택지

- **권장: 실제 Spend Cap ON과 사용량 여유 확인 후 기존 기능 범위로 활성화.** Storage/egress 포함량 초과 과금을 방지할 수 있으나 조직 전체 서비스 제한 가능성을 이해해야 한다. Compute 확장·새 프로젝트·유료 변환·부가 기능은 도입하지 않는다. 이 설정을 자동 변경하지 않는다.
- **설정 미확인: 로컬 구현만 진행하고 운영 기능은 비활성.** 확인 없이 ‘추가 비용 없음’으로 배포하지 않는다. 첨부만 끄더라도 본문 DB 저장·조회에 사용량이 생기므로 완전한 비용 보장이 되지는 않는다.
- **Spend Cap OFF 유지: 현재 포함량 여유만으로 무과금을 보장할 수 없음.** 비용 증가 없음이 절대 조건이면 운영 활성화는 보류한다. 다른 저장소로 옮겨도 DB/egress 비용 문제가 모두 없어지는 것은 아니다.

사용자에게 Spend Cap 현재 상태를 질문한 상태다. ‘모름’이나 기본 선택 상태는 제출된 답변/승인으로 취급하지 않는다.

## 배포 전 기록할 비밀이 아닌 확인값

- 실제 조직 플랜, 확인 날짜, Spend Cap ON/OFF.
- 청구 주기 Storage/egress 사용량 및 프로젝트 Disk Size 여유.
- Compute tier·Disk IOPS/Throughput·새 과금 항목 변경 없음.
- 비공개 버킷, 1MiB 제한, 허용 MIME 설정과 직접 접근 차단.
- 자동 삭제·탈퇴 삭제 실패 재시도 및 점유량 회수 확인.
- Supabase의 조직 제한이 기존 업무에 미치는 영향 확인.

API key·DB URL·token·로그인 세션·환경 파일 내용을 기록하거나 조회하지 않는다.
